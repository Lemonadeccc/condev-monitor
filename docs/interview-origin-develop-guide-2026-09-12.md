## 使用原则

第一人称只适用于你实际承担的工作。如果某部分是协作完成，就说“我负责 SDK，和后端同学一起确定消息契约”，不要把整仓实现都算作个人成果。公司背景、其他项目和任职年限按真实情况填写。

下面每个主题按“口述主回答 -> 实际代码流程 -> 三轮追问”组织。口述时先讲 60-90 秒，细节留给追问；不必背出每个默认数字。文中的示例时间、错误消息和测量公式是解释用例，不是已发生的生产案例或已测结果。

“当前实现”与“如果继续完善，我会怎样做”明确分开。能解释限制、故障路径和验证方法，比包装成“全部自动、不会丢、完全准确”更能体现实际理解。

### 自我介绍的三轮追问

**第一轮：你在平台里具体负责什么，不是团队做了什么？**

## 二、统一采集与分析链路

### 修订后的 STAR 主回答

**S：** 线上错误、性能指标和用户操作上下文分散时，排查需要反复复现。如果公司竞赛背景属实，可补充“比赛期间反馈窗口短，希望更快收集现场证据”，不要说监控能保证比赛不出问题。

**T：** 将浏览器采集、服务端接入、异步处理和管理页面串起来，同时区分事件分析数据与应用管理数据。

**A：** 我们使用 SDK 采集错误、性能和回放；DSN 做接入解析、限流和过滤。在 Kafka 模式下，把事件交给 Worker，再写入 ClickHouse；Postgres 保存应用等管理数据，Monitor API 提供管理接口。Dashboard 按需求调用两类 API。我的职责是【填写真实模块及跨端协作范围】。

**R：** 形成了可运行的错误、指标、回放和 AI 数据查询路径，接入和处理可以分别调整。这里的收益先表述为职责分离和功能复用；没有原始对照报告时，不声称吞吐提升三倍或查询下降 60%。

### 一次请求实际怎样流转

1. SDK 生成事件，上报到带 appId 的 tracking 地址；浏览器传输层补充事件标识和客户端时间。
2. DSN 解析数组或 Beacon 文本，做事件类型、UA、release、大小等检查，控制应用接入速率。
3. 普通事件包装为包含 appId、eventId、eventType、receivedAt 的消息。`ai_span` 等结构化 AI 事件走另一分支；`ai_streaming` 属于普通事件域。
4. Kafka 模式下普通事件、Replay 和结构化 AI 事件进入相应 topic；Worker 对普通错误计算 fingerprint，并尝试 Issue 处理。
5. Worker 分通道缓冲写入 ClickHouse。管理记录由 Monitor/Postgres 维护，不把账号事务放入事件分析表。
6. Bugs 页面请求 `/dsn-api/issues`，该 API 从 events 分组；Replay 页面走回放接口。不要把页面名称、HTTP 接口名和数据库表名混为一谈。

### 追问链 A：为什么这样拆

**第一轮：为什么 Postgres 和 ClickHouse 都要用？**

答：管理数据重事务更新、关联和归属校验；事件数据重追加和按时间聚合。按数据访问方式拆分比让同一套模型承担所有需求更清楚。但这不是说 Postgres 写不了事件，也不是分库分表，选型仍要结合实际数据规模。

**第二轮：Kafka 到底优化了什么？**

答：它把接入确认与后续处理解耦，提供一段持久缓冲，使 Worker 可以按自己的速度消费并批量写。代价是异步延迟、积压和恢复复杂度。Kafka 不会让 ClickHouse 无限吞吐，消费长期慢于生产仍会积压。

**第三轮：流量持续高于处理能力怎么办？**

答：应观察入站速率、消费速率、lag 的增长和最老消息等待时间，同时看 ClickHouse 写入耗时及资源。先限制低价值流量、优化批量和查询，明确容量上限，再决定扩实例或分片。当前单节点部署不能仅靠容器重启获得高可用，我不会把扩容方案说成已经实施过。

### 追问链 B：配置和降级

**第一轮：Replay 开关为什么还有一份在 ClickHouse？**

答：主配置由 Monitor/Postgres 管理，DSN 可以从 app_settings 读到简化配置；未命中或读失败再回退 Monitor。这是减少某些管理 API 调用的读取副本设计，不是新的配置权威，也没有证明 ClickHouse 一定更快。

**第二轮：修改开关后一定立即生效吗？**

答：不能保证。两处写没有共同事务，旧副本命中时也不会因为它过期而回源。SDK 初始化读取也不等于持续订阅。所以准确说法是尽力同步加回退，不是跨数据库强一致配置。

**第三轮：Kafka 挂了直写 ClickHouse，不就没有问题了吗？**

答：不是。当前普通事件和 Replay 有直写回退，但绕过 Worker 的 fingerprint/Issue 处理；AI 分支也不完全相同。它提高了部分原始数据的接收机会，却不保证聚合语义等价，还可能把压力转移给 ClickHouse。下一步应做有界降级和结果一致性测试，这是待完善项。

## 三、浏览器队列、生命周期与离线补报

### 修订后的 STAR 主回答

**S：** 逐条 Fetch 会产生较多请求，页面隐藏、卸载和弱网又会影响传输。

**T：** 在尽量不影响业务的前提下，减少普通事件请求次数，并给重要错误更快的发送机会和有限补报能力。

**A：** 普通传输拆为事件封装、内存队列、调度、发送通道和失败存储。错误进入 immediate 队列，普通指标批量调度；活动页面用 Fetch，隐藏/卸载尝试 Beacon 或 keepalive；可重试发送失败后尝试进入 IndexedDB，恢复条件满足时补报。只有该模块确由你负责时，再改为“我将传输层拆为……”。

**R：** 覆盖了普通批量、生命周期发送和失败重试机制。它是尽力交付，不是所有事件预先持久化的可靠消息系统，当前不能用代码推出 99% 的端到端成功率。

### 当前代码细节

1. immediate 立即请求 flush；批量达到默认 10 条或定时 5 秒触发，普通调度尽量用 idle callback。
2. drain 先取 immediate，再取 batch，因此一个错误可能把之前积累的性能事件一起带走，不是错误独占连接。
3. 活动状态 Fetch；隐藏/卸载且满足大小条件时尝试 Beacon，不适配再 Fetch keepalive。
4. 429 读取 Retry-After，设置冷却；网络、408、服务端错误属于可重试范围。其他 4xx 终止重试。
5. 发送失败后的批次记录含创建时间、重试计数、下次时间和 lease；普通失败存储默认最多 200 条批次记录、24 小时。
6. 补报受在线/可见约束，启动、定时和恢复网络等条件触发；领取有限记录顺序发送，没有持久队列里的错误优先排序。

lease 的具体作用：普通 FailureStore 在一次 IndexedDB readwrite 事务里，按 nextRetryAt 找到期记录并写入 leaseUntil，降低同一 origin 多标签页同时领取一批记录的概率。当前普通领取上限 10 条、lease 30 秒。它不是服务端幂等凭证，租约过期、响应丢失后仍可能重投；容量清理也在补报 worker 执行时进行，不是每次写入都有严格数量上限。

### 追问链 A：交付语义

**第一轮：sendBeacon 返回 true，数据就到了吗？**

答：只说明浏览器接纳排队，不是服务端确认，更不是 Worker 完成落库。Beacon 没有可读取的响应；因此需要区分客户端产生、浏览器接纳、DSN 接收和最终可查询四个阶段。

**第二轮：为什么还会发失败，不是小于 64KB 吗？**

答：除了单体大小，keepalive 还受同组在途请求的总预算限制。项目用 60000 字节作为普通 Beacon 判断门槛，不代表保留了独占额度；其他请求也可能占用额度，浏览器进程被终止也可能来不及发。

**第三轮：断网后马上关浏览器能恢复吗？**

答：这个版本不能保证。已离线时普通 flush 直接返回，事件仍在内存；只有可重试发送失败才尝试异步落 IndexedDB。还没持久化就关闭会丢。真正要覆盖硬关闭，需要在定义好的接纳点先持久化并验证恢复，但那是改进方向，不是现有能力。

### 追问链 B：重试会不会更糟

**第一轮：如何避免一直重试坏数据？**

答：先区分可恢复错误和永久拒绝，对 429 等尊重冷却，对可恢复失败使用有限预算和退避；本地记录有容量和寿命约束。永久 4xx 不应无限重试。但代码里把“停止重试”记成 ok，不等于业务接收成功，监控统计要特别区分。

**第二轮：那如何避免重复？**

答：相同事件重试需要保持稳定 eventId，服务端还要有匹配的幂等处理。仅仅每次请求成功后删除本地记录不够，因为服务端可能已收到但响应丢失。本项目保留事件标识不等于实现了数据库唯一事件约束。

**第三轮：有优先队列是不是能保证错误马上送达？**

答：优先级只是调度意图。当前发送中的 flush 会挡住新 flush，内存 drain 又会合并普通事件，离线补报也没有重新排序；所以不能保证严格时限。应测并发发送、只有错误没有指标和离线恢复等边界，而不是只测点击一次按钮成功。

## 四、错误指纹与多阶段候选归并

### 修订后的 STAR 主回答

**S：** 按原始 message 分组会被 URL、ID 和数字噪音拆散，文本很像的不同错误也可能被误并。

**T：** 提供可解释的确定性分组，并用语义相似度补充候选判断。

**A：** Worker 优先用堆栈生成 fingerprint，信息不足时用异常类型和归一化 message。在同应用候选中先查精确指纹，再用 MiniLM embedding 比较；灰区通过 TF-IDF 比较堆栈签名作第二意见。还有可配置的离线 LLM 归并确认与标题生成任务。

**R：** 当前有这套候选归并实现，但不能直接声称 Bugs 和邮件都消费了这个结果，也没有可核实的准确率提升数字。

### 实际判定过程

1. 对错误提取堆栈信息，过滤部分库帧，生成确定性签名；没有可用堆栈才退化到异常类型和归一化文本。
2. normalization 替换 UUID、时间戳形数字、URL、数字及多余空白。它在计算前使用，不是先查指纹再单独补做。
3. 查询同 app 最近 20 个 open Issue，先在该集合内匹配 fingerprint。
4. 没命中则构造 embedding 输入，对候选向量做余弦相似度；默认大于等于 0.92 选择该候选。
5. 默认 0.85 到 0.92 的灰区再看 TF-IDF，比较双方 stack signature 帧集合；达到默认 0.8 才选择。
6. 没选中时创建确定性 ID 的 Issue 并保存向量；选中时更新状态行的时间。原始 events 仍然按自己的 fingerprint 写入，不能推导语义归并已改变页面分组。

计算细节：MiniLM 默认输出 384 维向量，使用 mean pooling 和 normalize；余弦相似度是 `dot(a,b) / (norm(a) * norm(b))`。TF-IDF 先对堆栈帧分词，当前 TF 是 `某词次数 / 当前词数`，IDF 是 `log((文档数 + 1) / (含该词文档数 + 1)) + 1`，再对加权稀疏向量求余弦。它不是另一个 LLM；当前每次比较都会更新进程内文档频率，分数会受调用历史影响，不能说是固定训练好的全局模型。

### 追问链 A：规则为什么有效，又为什么会错

**第一轮：为什么堆栈优先，不直接比较 message？**

答：message 经常包含动态参数，相同调用位置可能更有区分力。但堆栈也会受打包、版本、sourcemap 和公共包装层影响，不是根因的绝对真值。这个策略首先追求确定性和可解释性。

**第二轮：把所有数字和 URL 都替换，不会误合并吗？**

答：会。例如状态码 401 和 404、两个不同 API 地址可能有不同根因。规则去噪同时损失区分度，不能认为归一化越激进越好。当前就是较粗规则；若继续优化，应保留有判别力的结构字段，再用真实样本评估，而不是宣称已完全解决。

**第三轮：0.92 和 0.85 怎么来的，0.92 是 92% 准确吗？**

答：不是，余弦相似度不是正确概率。当前是代码配置阈值，没有原始标注报告时不能说是我通过大规模样本调出的。合理评估应准备同根因/不同根因标注，分开看误并和裂化，并按时间或版本分离训练调参集与验证集。

### 追问链 B：语义增强是否真的落到产品

**第一轮：这里是向量数据库全量搜索吗？**

答：不是。当前是最近 20 个 open Issue 候选，Worker 本地算余弦相似度，连精确指纹匹配都受该候选窗口影响。TF-IDF 语料也在进程内，重启和多实例会有差异。

**第二轮：那 Bugs 里的 Issue 数就是这些候选合并后的数量吗？**

答：不是当前版本。Bugs 请求 `/dsn-api/issues`，它对 events 按 fingerprint 及其他字段分组，没有读取 Worker 选定的语义 Issue ID。这个区别必须说清楚，不能把 Worker 算法的存在当成产品已闭环的证明。

**第三轮：你说减少告警，是怎么关联的？**

答：当前邮件在 DSN 接入阶段按应用节流，不依赖 Worker 语义结果，所以不能把告警减少归因于 embedding。离线 LLM 虽然有实现，也不是“每天把所有不确定问题交给人工再自动学会”的完整反馈系统。

## 五、确定性 ID、ClickHouse 收敛与 Kafka 恢复

### 修订后的 STAR 主回答

**S：** 同 fingerprint 在并发处理或重投时，随机创建 Issue ID 容易产生多个问题实体。

**T：** 让相同应用与 fingerprint 尽量落到相同 Issue 标识，降低重复实体风险。

**A：** 实现以 appId 与 fingerprint 为输入的确定性内部 ID，并在 Issue 表使用 ReplacingMergeTree 保存版本，需要收敛视图的查询使用 FINAL。

**R：** 这解决的是同键 Issue 标识和版本收敛，不是原始事件完全幂等。当前 Kafka 位点提交存在配置缺口，不应将其包装成已经完成的高并发去重/恢复体系。

### 三种“重复”必须分开

1. 相同问题实际发生了十次：这是十次真实发生，应保留发生次数，不能按相同 fingerprint 删除九次。
2. 同一次事件因为网络重试收到两次：应依靠同一个 eventId 识别重投，需要事件级幂等。
3. 同一个 Issue 的状态写了多个版本：这是 Issue 行版本收敛，ReplacingMergeTree 处理的是这一层。

### 追问链 A：ID 和 FINAL

**第一轮：具体怎么生成 ID？**

答：把 appId、NUL 分隔符和 fingerprint 拼成输入，用 SHA-256，再截取和组装为 UUID 格式。加入 appId 避免同指纹跨应用混用；分隔符避免简单拼接导致输入边界歧义。输入格式稳定同样重要。

**第二轮：那这是标准 UUIDv5 吗？**

答：不是。标准 UUIDv5 用 namespace/name 的 SHA-1。当前虽然设置了 v5 版位，但算法是 SHA-256，应称自定义确定性内部 ID，不能因为外形像 UUID 就说符合 UUIDv5 标准。

**第三轮：ReplacingMergeTree 能保证唯一并正确累计次数吗？**

答：不能。它按 ORDER BY 的同键替换版本，后台合并不是即时唯一约束；FINAL 在查询时处理版本，也有成本。它不会把并发写入的 count 自动相加，同秒版本和状态覆盖还要另外定义规则。Issue 收敛不能代替事件去重或事务计数。

### 追问链 B：消息恢复

**第一轮：处理一条消息什么时候可以提交 offset？**

答：设计原则是这条消息要求的结果已经持久化，或已进入可信的持久失败处理路径，才提交对应分区连续完成前缀的下一个 offset。不能只因为放入内存 buffer 就提交，也不能跨过前面失败的消息。

**第二轮：当前代码是不是这样实现了？**

答：意图是 flush 后再调用 commit hook，但实现不完整。autoCommit 关闭，调用无参数 commitOffsetsIfNecessary，又没有 interval/threshold；KafkaJS 2.2.4 中这些条件不满足就不实际提交。现有实现不能当作已验证的恢复保证。

**第三轮：你准备怎么证明修复正确，而不是改一行？**

答：先测试 flush 返回时关联消息是否真的全部持久化，再验证真实 broker 的 committed offset。注入落库前崩溃、落库后提交前崩溃、提交后重启和重平衡；按唯一 eventId 核对原始事件和派生结果。同时检查暂时存储故障是否被误丢到无人重放的 DLQ。这是验证计划，本轮没有执行这些生产恢复实验。

## 六、错误触发的 Session Replay

### 修订后的 STAR 主回答

**S：** 错误堆栈只能解释程序位置，复杂交互问题还需要错误前后的页面状态和操作上下文。

**T：** 提供诊断用回放，同时控制录制、上传和敏感信息范围。

**A：** 我们采用 rrweb 的 DOM 快照与增量事件，在应用开启后懒加载录制。平时维护有限缓冲，错误发生时截取前后窗口；错误事件与回放共享 replayId，播放端支持跳到记录的错误时点。默认输入掩码、不开 canvas，并设置事件数和失败缓存约束。

**R：** 可以把错误与对应现场联系起来，而不是只看堆栈。当前浏览器上传是 JSON，没有 gzip 压缩；体积和可回放率需测试后再量化。

### 从录制到播放的实际流程

1. SDK 配置开启 Replay，并取得服务端 replayEnabled，才加载 rrweb。若加载被扩展拦截，普通错误仍能上报，但不会有录制。
2. 默认前窗 15 秒、后窗 10 秒，目标 buffer 90 秒、最多 3000 个事件；每 10 秒 checkout 生成全量基线。
3. 捕获普通 error 或失败 AI 流事件时生成 replayId，保存第一个错误时间，并启动后窗计时器。白屏发送 error 类型，所以也能触发。
4. 计时器到期或 pagehide 时截取数据，寻找窗口开始前最近的 FullSnapshot，并尽量带上 Meta 与后续增量。
5. 独立 POST 回放 JSON；离线/可重试失败进入 Replay 自己的失败队列，默认保留预算 20 条、24 小时，另有有限重试。
6. DSN 再限制 events 数为 2000，截断附加 snapshot 字符串后入库。播放器用事件时间基线计算 errorAt 的相对位置。

### 追问链 A：为什么不能直接切数组

**第一轮：rrweb 是录像吗？**

答：它记录 DOM 快照和后续变化、鼠标输入等事件，再在播放环境重建，不是把屏幕编码成视频。这种方式能关联 DOM 操作，但不等于像素级完整录屏，canvas、跨域内容或资源失效都会影响还原。

**第二轮：为什么必须保留 FullSnapshot？**

答：增量事件可能只描述“修改编号为 X 的节点”。没有先前的全量快照，播放器可能不知道 X 对应什么。截取窗口时需要基线和连续增量，不能只拿最近 N 条。这也是实际片段可能比目标前窗更长的原因。

**第三轮：前端 3000、后端 2000，能保证完整吗？**

答：不能。上限控制成本，但不等于完整性证明。截掉必要增量可能损害还原，附加 snapshot 字符串截断也不是完整 DOM。应该用基线存在、增量引用、错误时点覆盖和实际播放检查定义“可用”，不能只看 HTTP 200 或数组非空。

### 追问链 B：连续错误与错误跳点

**第一轮：连续点 20 秒，会产生多少个回放？**

答：不是一错一份。首个错误打开 10 秒后窗，pending 期间后续错误共用 replayId；该窗口清理后再发生错误才创建下一份。约 20 秒连续操作通常涉及约两段，边界点击、计时器延迟、pagehide 和上传失败都会影响实际段数，不能只按总秒数承诺固定上传数。

**第二轮：两段会有重叠吗？**

答：会。举例说明，已持续录制时，100 秒出错目标窗口是 85-110 秒；110.1 秒的新错误窗口是 95.1-120.1 秒，两段前后文就有重叠。实际还会因 FullSnapshot 基线调整。重叠有利于每段独立理解上下文，但增加数据量。

**第三轮：同一段关联多个错误，Jump to error 跳哪个？**

答：当前段只保存首个触发错误的 errorAt，后续错误复用 replayId，不更新它；播放器跳到这个首错误相对首事件的时间偏移。它不是每个关联错误都有独立标记，也不会随着连续点击一直延长后窗。

### 可复习的本轮协作排障记录

本次实际调试中出现过：普通错误和指标已有数据，Replay 却为空；控制台显示 rrweb 动态模块请求 `ERR_BLOCKED_BY_CLIENT`。关闭 localhost 上的扩展拦截后，用户确认 Replay 出现。由此能支持“扩展拦截导致录制模块未加载”，但没有单独隔离出究竟是哪一个扩展。

这是本轮用户与助手的协作调试记录，只有你实际参与、能说明自己的操作和观察时，才可作为个人案例。口述可说：“协作排查时把问题分成录制、上传、入库、查询四段；普通事件成功不代表 rrweb 已加载。最后检查到动态模块被客户端拦截，在 localhost 停用拦截后复测恢复。我实际负责的是【填写本人操作】。”不要改写成独立解决的生产事故，也不要说是自己修复了 rrweb 版本。

## 七、白屏检测

### 修订后的 STAR 主回答

**S：** 页面没有有效业务内容时，不一定会出现 JavaScript 异常，只监听 error 会漏掉这类现象。

**T：** 增加一种成本可控的疑似白屏信号，供排查结合错误、资源和回放确认。

**A：** 当前实现是九点 DOM 命中采样。load 后延迟检查，所有点都命中 html、body、配置根容器或空元素时报告；可选开启路由/点击后的短窗口 MutationObserver 检查，并对 mutation 防抖。

**R：** 覆盖了一部分空壳页面场景，不是像素识别，也不保证所有白屏。不能说基于 Performance API 计算，更不能把检测等同于防止白屏发生。

### 具体判定流程

1. 等待 load 或页面已 complete，默认延迟 1 秒开始。
2. 把九个相对坐标换算为视口坐标，逐点调用 elementFromPoint。
3. 将命中元素与 html/body/配置 wrapper 比较，记录元素简易 selector 和命中信息。
4. 所有点都视为空壳才上报；最多尝试三次，每次间隔一秒，并不是连续三次白屏才确认。
5. 上报 event_type=error、type=whiteScreen、reason、path 和采样结果，与普通错误链路关联。
6. 当前实例 hasReported 后不再重复上报；runtimeWatch 默认关闭，不能直接声称所有路由都持续检测。

### 追问链 A：误报与漏报

**第一轮：为什么不用 root.innerHTML 判断？**

答：有 HTML 不代表视口内有有效内容。采样命中比单纯判断字符串为空更贴近可见结构，但它仍只是 DOM 启发式，不知道用户看到的是不是有意义的内容。

**第二轮：白色 canvas 或一个覆盖全屏的空 div 呢？**

答：如果命中普通非 wrapper 元素，算法可能认为不白屏，即使视觉上全白。反过来极简布局的采样点全落到空壳也可能误报。需要结合实际业务布局校准，不能把九点全命中当成视觉真相。

**第三轮：把骨架屏放白名单不就解决了？**

答：当前 wrapperSelectors 不是“忽略报警”的白名单，而是“把它算作空白”的集合。把骨架屏加入可能增加误报。若要区分 loading 和异常空壳，需要单独的加载状态、稳定窗口或超时规则；本版本没有完整的骨架屏识别体系。

### 追问链 B：运行时与性能

**第一轮：路由跳转后怎么触发检查？**

答：显式开启 runtimeWatch 后，点击、popstate、hashchange 以及 pushState/replaceState 会打开短时观察窗口。DOM 变化防抖后检查，默认窗口约 10 秒、debounce 200ms；没有开启时主要是首屏检测和手动 trigger。

**第二轮：MutationObserver 常驻监听会影响页面吗？**

答：当前设计是限定观察窗口，不在每次 mutation 里做重分析；触发后做九点命中检查。仍有主线程开销，需要在高 mutation 页面测调用次数和耗时，不能仅凭“有 debounce”就说零影响。

**第三轮：一个 SPA 第一次白屏恢复后，第二次白屏也会上报吗？**

答：当前同一 WhiteScreen 实例不会，hasReported 已经锁定并停止观察。按路由恢复检测预算、重新报告属于需要另行设计的能力。面试应把“具备运行时入口”和“每路由完整覆盖”分开说。

## 八、隐私采集约束

### 修订后的 STAR 主回答

**S：** Replay 和 AI 上下文对诊断有帮助，但也可能包含输入、用户信息和业务内容。

**T：** 在采集入口减少非必要内容，避免把所有原始上下文默认上传。

**A：** Replay 默认输入掩码，并提供文本掩码 class 与区域 block 规则；Vercel 自动语义适配器默认不采 prompt/tool 内容。DSN 另外做入站拒绝与大小治理，但这不是字段脱敏。

**R：** 已具备局部的保守默认策略。当前 Next 异常补报还有 input 旁路，不能宣称统一全链路脱敏、完全合规或风险下降 90%。

### 实施时要能解释的检查顺序

1. 先区分字段：结构化耗时、模型名，与 prompt、DOM 文本、邮箱、请求参数不是同一敏感程度。
2. 找每条实际生产数据的入口，而不是只看一个 privacy 配置类型：Replay、OTel、callback、手工 error/cancel 都要查。
3. 核对配置真正在哪一步生效：录制前屏蔽，还是事件构造后删除，是否在落本地缓存之前处理。
4. 检查正常、异常、取消、重试是否走相同策略；本项目目前并非所有路径统一。
5. 如果做审计，用合成敏感标记检查网络、本地失败队列、后端日志和数据库；这是可执行的验证方法，不是本轮已完成的审计结果。

### 追问链 A：掩码的范围

**第一轮：maskAllInputs 是否意味着所有敏感内容都不会录？**

答：不是。它主要覆盖输入内容；普通 DOM 文本、URL、图片和自定义 metadata 要另行约束。blockSelector 可以屏蔽区域，maskTextClass 可以覆盖指定文本，但是否匹配业务敏感区需要实际验证。

**第二轮：为什么不全部上传后再服务端脱敏？**

答：那时明文已经经过客户端缓存、网络和接入日志。能在采集源头减少就先减少，服务端再做补充。当前已有部分录制/适配器入口控制，但不能说服务端已经有全路径兜底脱敏。

**第三轮：默认 capturePrompt=false，异常还会带 messages 吗？**

答：当前可能会。Next wrapper 的错误、取消、工具失败补报直接使用 options.input，示例传的是 messages；它不是同一个自动适配器开关控制的路径。这是明确缺口，不能靠默认开关名称推断数据安全。

### 追问链 B：怎样衡量隐私治理

**第一轮：UA、release 黑名单怎么降低敏感字段泄漏？**

答：它们是整条拒绝策略，不是遮盖字段。可以减少不需要的流量，但不能作为“敏感内容已脱敏”的证据。

**第二轮：那“隐私风险降低 90%”怎么证明？**

答：单一百分比没有明确风险模型，很难成立。更可验证的是定义敏感字段集、路径覆盖矩阵和合成样本，记录未经允许的明文是否出现。没有审计记录时，我不报这个数字。

**第三轮：所有字段都遮掉就算合规了吗？**

答：也不能这么推导。访问授权、租户隔离、保留和删除、用户告知等是不同职责，字段掩码只解决一部分。这个版本不应声称完成全部合规要求。

## 九、AI 网络时序与服务端语义关联

### 修订后的 STAR 主回答

**S：** AI 流式响应有等待首块、持续卡顿、中途断流等问题，单看 HTTP 成功失败不够。

**T：** 同时观察浏览器收到流的时间线，以及服务端模型调用的结构化上下文。

**A：** 浏览器可选开启 fetch/SSE 探针，对响应副本读流，记录首块、结束、间隔、字节和失败阶段。服务端通过 AI SDK 的 OTel/callback 适配补充模型、provider、usage 和 finish reason，并显式传播 traceId 进行关联。Next 示例分别注册客户端和服务端，再包装 AI 路由。

**R：** 能在数据齐全时区分浏览器传输表现与模型调用语义，但不是前端一个 init 自动理解全部 AI 业务；当前双采集、异常状态和隐私边界仍需完善，也没有定位效率提升 50% 的可核实样本。

### 一条 Next AI 请求怎样关联

1. instrumentation-client 注册浏览器监控，配置实际 `/api/chat` 路径；流探针不是对所有普通 Fetch 强行读取语义。
2. 命中规则且同源或在允许列表内时，将 traceId 注入请求头；跨域还要求服务端 CORS 允许该头。
3. 服务端 instrumentation 在 Node 运行端注册 reporter/适配器；浏览器初始化不等于服务端已注册。
4. AI 路由使用 streamTextResponseWithCondev，读取请求 traceId，补充 sessionId/userId 等显式业务上下文。
5. wrapper 将 condevTraceId 写进 AI SDK telemetry metadata，语义适配器再读出，不能假定 OTel span 自然知道浏览器 ID。
6. 浏览器返回原始 Response 给业务，探针消费 clone；服务端结束时采语义事件，DSN 查询按 traceId 关联网络与语义数据。

### 追问链 A：你到底测了什么

**第一轮：sseTtfb 是首 token 时间吗？**

答：不是。代码从发起 fetch 计时，到副本 reader 第一次读到响应体字节块。这个块可能是心跳、协议字段，也可能含多个模型增量。严格 HTTP TTFB、模型首输出和用户看到首字应分别定义。

**第二轮：chunkCount 能当输出 token 数吗？**

答：不能。网络 chunk、SSE frame 和模型 token 是三个层次，分包会合并或拆分。token 优先用 provider/AI SDK 返回的 usage，没有就标未知；像 Python 示例的 tokenizer 估算要明确是估算，不能当真实计费。

**第三轮：流结束了是否表示模型成功，卡顿是否一定是模型慢？**

答：都不一定。网络正常结束可能携带业务错误，慢间隔可能来自模型、代理缓冲、网络或浏览器调度。还要结合 finishReason、服务端状态和完整性信号。probe 达自身上限会结束观测，不等于业务完成，更不能把采集器取消记为用户取消。

### 追问链 B：接入和资源成本

**第一轮：clone 为什么不会把业务的流读掉？**

答：业务拿原 Response，探针读 clone 的分支，而不是直接占用同一个 reader；不会为了探针再请求一次模型。但 tee 分支有内存和背压影响，因此只能说尽量保留业务消费语义，不能说完全无侵入。

**第二轮：无限流会不会一直占资源？**

答：当前有累计块数和字节上限，默认 50000 块、10MiB，但没有独立持续时长 watchdog；这些检查还发生在读到块之后。很慢、永不结束的流仍是需要处理的边界，不能认为有字节上限就解决所有长连接问题。

**第三轮：服务端同时有 callback 和 OTel，是不是越多越完整？**

答：不是。当前注册具备两边同时产数的条件，而没有统一去重合同；部分 OTel 映射也没有完整父子关系和错误状态。因此增加采集器可能重复，不等于更准确。合理方向是确定主采集策略并验证重复、异常与取消，但这里不把后续方案说成已完成。

## 十、贯穿项目的补充追问

### A. 为什么不是一个 init 包办所有 AI 监控

**第一轮：你能把接入做成一行吗？**

答：普通浏览器能力已经接近一次 init；完整 AI 链路至少区分浏览器与服务端两个运行环境。服务端还要挂上模型/框架适配器，业务身份和检索步骤不能靠 SDK 猜。

**第二轮：中间件、适配器、装饰器各做什么？**

答：HTTP 中间件适合请求上下文和请求时序，模型适配器采 usage/模型/结束原因，函数包装或装饰器适合显式标记检索等业务步骤。不要让 HTTP 中间件猜模型 token，也不要让普通函数装饰器代替整个流生命周期。

**第三轮：流式函数 return 了就能结束 span 吗？**

答：不能，返回 Response 或生成器可能只是开始消费。必须观察迭代完成、异常、取消和资源关闭。当前 Python SDK 有显式 trace/span/generation 与部分上下文管理器，没有通用 observe 装饰器或完整 FastAPI 自动接入层；这些只能作为后续方向。

### B. 代码体现什么设计模式

**第一轮：为什么不写一个大 send 函数？**

答：封装、排队、调度、选择通道和持久重试有不同变化原因。当前 BrowserTransport 组合了这些组件，便于替换发送器和测试时钟/存储，不是为了多写类。

**第二轮：具体能对应哪些模式？**

答：Fetch/Beacon 的选择可以用策略思想理解；对不同 AI SDK 数据的统一转换是适配器；Next 的组合入口接近外观模式；Replay 的 before-enqueue 是拦截器扩展点。核心是职责和依赖方向，不是给每个文件贴模式标签。

**第三轮：符合模式就意味着设计没问题吗？**

答：不是。两个采集适配器重复产数、补报绕过隐私、flush 不代表完整持久化，都是跨组件契约问题。模式不能替代生命周期、不变量和故障测试。我会优先修契约，而不是再叠一个“大中间件”。

### C. 为什么不加 Redis、ES、分库分表

**第一轮：监控平台为什么还没 Redis？**

答：当前应用限流是进程内 token bucket，多实例下不是严格全局额度。如果明确需要跨实例共享原子限流或低延迟缓存，Redis 才有清晰用途；不能因为是监控平台就自动加一个必需依赖。

**第二轮：错误检索不用 ES，ClickHouse 分区不是分片吗？**

答：当前重点是按应用、时间和字段聚合。复杂全文检索是否需要 ES，要看现有查询是否满足目标；增加索引系统也增加同步成本。分区是表内数据组织，分片是把数据分散到不同节点，两者不能混用。

**第三轮：现在最该补什么？**

答：先是读接口授权、隐私旁路、消费恢复和有界故障处理，再看容量数据。重试不是熔断，容器重启不是高可用，分片也不是副本。没有这些边界，新增组件只会把故障链路变长。

### D. Sourcemap 怎样还原，不是上传了就行吗

**第一轮：线上压缩堆栈怎样找到源位置？**

答：发布时把对应 map 上传，按 appId、release、dist、minifiedUrl 等定位文件，再将压缩文件行列映射到原始源位置。本项目 Monitor 存元数据和文件，DSN 用 trace-mapping 解析并做有限缓存。

**第二轮：为什么必须关联 release？**

答：同一个资源路径在不同发布可能对应不同内容，错版本 map 会给出错误源位置。缓存只减少重复读取，不能修正上传版本和事件上下文不匹配。

**第三轮：找不到 map 怎么办，直接丢错误吗？**

答：不应该让可选还原能力决定原始错误是否保留。当前缺 release 或匹配 map 时无法补出原始帧，排查仍需看原始异常。并且查询时堆栈还原不等于 Worker 指纹生成时已使用同一份还原结果，不能混淆这两步。

## 十一、成果数字应该怎样回答

原稿“你怎么得到这个数据”的八段不能靠改得更像测试流程就当成真实历史。下面是**测量方案和口径**，未拿出报告前不要把“应当测”说成“我已经测过”。

| 成果项        | 应怎样定义和测量                                                                        | 常见错误                                                    |
| ------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 吞吐          | 相同机器、payload、数据量和并发下，稳定窗口内最终持久化的唯一事件数/秒；同时记录 lag    | 用 HTTP 接收 QPS 代替落库吞吐；消费永远追不上还说吞吐高     |
| 查询时延      | 固定 app/time range/数据集，区分冷热缓存，记录 P50/P95/P99 和错误率                     | 只取少量平均值；同时换机器、清空数据后归因于 Kafka          |
| 丢失和成功率  | 分场景生成可核对 ID，在固定恢复等待窗口后比对唯一落库事件；单列采样、永久拒绝、缓存淘汰 | 把 Beacon true、HTTP 200、FetchSender ok 当端到端成功       |
| 聚合质量      | 人工标注同根因关系；同时看误并 precision、裂化 recall，或适合聚类的指标                 | 把相似度 0.92 当 92% 准确；只看 Issue 数变少                |
| 告警减少      | 固定输入错误集、规则和发送策略，数实际成功通知，并检查漏报                              | 当前告警不读语义 Issue，却归因于 embedding                  |
| 重复写入      | 分开测事件重投、同 fingerprint 多 ID、同 Issue 版本冗余；说明 merge 前还是 FINAL 后     | 把十次真实错误当成九次重复消息；用 FINAL 隐藏行就说写入减少 |
| Replay 体积   | 同场景、同录制时长口径下比较实际请求字节；单列事件裁剪、窗口减少和压缩                  | 把短窗口对比整会话称“压缩率”；比较 JSON 字符数而非字节      |
| Replay 可用率 | 预定义基线、关键交互、错误时点覆盖和播放成功条件，统计合格样本/总样本                   | 只看上传成功；“95% 还原准确”没有可判定标准                  |
| 白屏质量      | 真白屏、正常 loading、骨架屏、极简页、路由过渡的标注样本，分别报漏报与误报              | 未说明误报率分母；只测试 root 清空这一个场景                |
| 隐私控制      | 合成敏感标记在各路径/状态/存储里的暴露检查，报告覆盖与违规项                            | 用 payload 黑名单代替脱敏；随意量化“风险降低”               |
| 定位效率      | 定义从反馈到根因确认的开始/结束点，提供可比案例、样本量和分布                           | 把页面打开快等同于诊断快；把主观反馈当 50% 数据             |

**公式示例，不是项目实测：** 查询降幅是 `(旧耗时 - 新耗时) / 旧耗时`；吞吐达到原来三倍是 `新 / 旧 = 3`，相对增长是 200%，不要含糊说“提升三倍”。丢失率从 5% 到 1% 是相对下降 80%、减少 4 个百分点；它与“成功率 99%”可以数学一致，但这种一致不能证明实验发生过。

如果暂时没有资料，可以坦诚回答：“这份代码能证明机制存在，但我目前没有可以核验的历史对照报告，所以这里不报精确百分比。我可以具体说明实现、演示场景和应怎样测量。”不要说“取个稳妥平均值”来代替测量定义。

## 十三、面试前的复习路径

1. 先明确本人负责范围，以及每项“已实现/待完善/未测量”的边界。
2. 沿着一条普通错误读：errorsIntegration -> transport -> DSN tracking -> ingest writer -> Kafka consumer -> ClickHouse -> Bugs 查询。
3. 沿着一条 Replay 读：应用开关 -> rrweb 加载 -> pending 窗口 -> snapshot 选取 -> 独立上传 -> 播放器 errorOffset。
4. 沿着一条 AI 请求读：浏览器 header -> Next wrapper metadata -> 语义 adapter/callback -> 入站分类 -> 查询关联。
5. 在本地测试环境自行演练“普通错误有、Replay 无”“断网后关页”“连续错误”“骨架屏”和“AI 取消”，保留真实记录后再把它们整理成案例。不要在生产环境造流量、发送告警或调用付费模型来凑面试素材。
6. 复述每条链的失败边界，能够回答“哪个阶段成功了、哪个阶段还不知道”，而不是只记组件名字。
